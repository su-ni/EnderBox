# 长任务盘点：哪些操作需要进度、现在的进度机制有几套

> 盘点日期：2026-10-09。方法：**grep 实际注册的路由**（`mux.HandleFunc`）+ 读现有进度实现，
> 不凭印象列。起因：用户要「为所有需要进度展示的功能加气泡进度，**细到单文件**」。

---

## 一、现在有几套进度机制？—— **四套，各写各的**

| # | 机制 | 位置 | 谁在用 | 前端表现 |
|---|---|---|---|---|
| 1 | **下载任务表** | `internal/fetch/*.go`（`GET /api/fetch/tasks`） | 服务端 jar / Java / 模组下载 | `DownloadBar.tsx` 右下气泡 + `DownloadCenter` 台账 |
| 2 | **整合包作业表** | `internal/modpack`（`GET /api/modpacks/ops`） | 升级、安装整合包 | `ModpackOpView.tsx` + 气泡 |
| 3 | `Progress` 类型 | `internal/modpack/executor.go` | 上面第 2 套内部用 | — |
| 4 | SSE 日志流 | `/api/instances/{id}/logs` | 控制台实时日志 | `ConsolePage` |

⚠ **四套协议不统一**：字段名、轮询方式、取消语义、前端渲染组件都不同。
用户要「所有功能都加进度」——如果继续一套一套加，会变成七套八套。
**建议先抽一个通用作业框架，把长任务统一接上去**（见第四节）。

---

## 二、长任务全清单（按「会不会真卡住用户」排序）

耗时是我按**数据量**估的档位：秒级 / 十秒级 / 分钟级。分钟级＝必须异步，否则浏览器转圈到超时。

| 操作 | 路由 | 耗时档 | 现在 | 备注 |
|---|---|---|---|---|
| **备份创建** | `POST /backups` | **分钟级** | **同步** ✗ | 打包整个 `world/`，几 GB 很常见。**最痛的一个** |
| **备份还原** | `POST /backups/{file}/restore` | **分钟级** | **同步** ✗ | 解压回去 + 可能先备份当前档 |
| **整合包升级** | `POST /modpack/upgrade` | 分钟级 | **异步 ✓** | 已有气泡，标杆 |
| **整合包安装** | `POST /modpacks/install` | 分钟级 | **异步 ✓** | 同上 |
| **导出整合包** | `POST /modpack/export` | 秒~分钟级 | **同步** ✗ | 逐个算 sha1 + 分批反查 + 打 zip |
| **服务端格式转换** | `POST /convert` | 分钟级 | **同步** ✗ | 换核心，要搬文件 |
| **导入已有服务器** | `POST /import` | 秒~分钟级 | **同步** ✗ | 扫描 + 可能移动/复制大量文件 |
| **导入扫描** | `POST /import/scan` | 秒~十秒 | 同步 ✗ | 遍历目录树 |
| **文件解压** | `POST /files/extract` | 秒~分钟级 | **同步** ✗ | 大压缩包 |
| **文件上传** | `POST /files/upload` | 秒~分钟级 | **同步** ✗ | 大文件；**这个最该有进度条** |
| **文件复制 / 移动** | `POST /files/copy` `move` | 秒~分钟级 | **同步** ✗ | 整个 world 目录搬一次就是分钟级 |
| **批量删除** | `POST /files/batch-delete` | 秒级 | 同步 | 文件多时会慢 |
| **插件按 URL 安装** | `POST /plugins/install-url` | 秒~分钟级 | 需确认 | 要下载 + 落地 |
| **Java 下载** | `POST /java/download` | 分钟级 | **走 fetch 表 ✓** | 已有气泡 |
| 配置还原 | `POST /configs/restore` | 秒级 | 同步 | 可以最后做 |
| 服务端 jar 切换 | `POST /server-jar` | 秒级 | 同步 | 可以最后做 |
| 启动 / 停止 / 强杀 / 重启 | — | 秒~十秒 | 同步 | **不需要**（有状态点，本来就在等） |
| 玩家操作（白名单/OP/封禁/踢） | — | 毫秒 | 同步 | **不需要** |
| 游戏规则、属性、配置读写 | — | 毫秒 | 同步 | **不需要** |

**结论**：真需要进度的有 **9 个**（分钟级 5 个 + 秒~分钟级 4 个）。

## 三、「细到单文件」意味着什么

用户要求进度**细到单文件**（不是只有「正在扫描…」这种阶段文案）。这要求每种操作都能报
**`已完成 N / 总数 M`**，逐条对照：

| 操作 | 能不能数出总数 | 怎么数 |
|---|---|---|
| 备份创建 | ✓ 可以先扫一遍要打包的文件 | 遍历一次目标目录 |
| 备份还原 | ✓ zip 里有 entry 总数 | 读 zip 目录 |
| 导出整合包 | ✓ 扫描时就拿到了文件列表 | `len(files)` |
| 文件上传 | ✓ 按字节数（前端也知道总大小） | `Content-Length` |
| 文件解压 | ✓ zip entry 总数 | 同上 |
| 文件复制/移动 | ✓ 遍历源目录 | filepath.Walk |
| 格式转换 | ✓ 文件数 | 同上 |
| 导入实例 | ✓ 扫描结果就是总数 | 已有 scan |
| 插件按 URL 安装 | ✗ **只有 1 个文件** | 不需要「单文件」，用字节进度 |

⚠ 一个容易漏的点：**「单文件」不等于「字节级」**。复制一个 3GB 的 `level.dat` 时，
按文件计是「1/1 完成」但实际还在写 —— 所以**大文件要按字节报**，或者至少**文件 + 字节双口径**。
这一条实现时别省。

## 四、建议的做法（先统一，再铺开）

### 4.1 抽一个通用作业框架

现在四套机制里，**第 2 套（`modpack` ops）最完整**：有作业 id、阶段、百分比、取消、
完成/失败、前端渲染组件。**以它为准抽出来**，放到 `internal/jobs`：

```go
type Job struct {
    ID        string
    Kind      string      // "backup" / "export" / "extract" / "upload" ...
    Title     string
    Total     int64       // 总文件数（或总字节）
    Done      int64
    Stage     string      // 人类可读的当前阶段
    Current   string      // 当前正在处理的文件（用户要的「细到单文件」）
    State     string      // running / done / failed / canceled
    Err       string
    StartedAt time.Time
}
```

统一三条路由：`GET /api/jobs`（列表，给气泡）、`GET /api/jobs/{id}`、
`POST /api/jobs/{id}/cancel`。

### 4.2 前端统一一个气泡

把 `DownloadBar` 与 `ModpackOpView` 的气泡合并成一个 **`JobBar`**，
所有作业（下载、备份、导出、解压…）都往它上面挂。**一个位置、一套样式、一种交互**。

### 4.3 推进顺序（按「真卡住用户」排）

1. **备份创建 / 还原** —— 分钟级且现在是同步，最痛
2. **导出整合包** —— 刚做的，顺手接上（先把框架立起来）
3. **文件上传 / 解压 / 复制移动** —— 用户会盯着进度条等的那些
4. **导入实例 / 格式转换**
5. 收尾：配置还原、server-jar 切换

## 五、待确认

1. **范围**：是上表那 9 个都做，还是先做前三个？
2. **要不要先立框架**：直接给导出加个专属进度也能做，但后面每个功能都要重写一遍；
   抽 `jobs` 前期多花一点，后面全是接线。
3. **取消语义**：现在只有下载和整合包作业支持取消。备份/导出做到一半取消，
   要不要清理半成品（`.part` / 半个 zip）？
