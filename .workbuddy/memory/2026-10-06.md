# 2026-10-06

## 插件自动注入：设计定型（grill-me 走完全部分支）

用户上一轮点的方向是「插件服务器时自动塞入插件」，这一轮把设计钉死了。
**结论：砍掉 Tier 0（不读 NBT），只做一套自研 Bukkit 插件。**

### 一、锁定的决策

| 项 | 决定 |
| --- | --- |
| 数据范围 | 实时坐标、背包+末影箱、血条/饥饿/经验/维度、皮肤（仅正版服） |
| 读写 | **要能写**（给物品 / 清背包 / 传送） |
| 通道 | **双向文件**：插件写 `snapshot.json`，面板写 `cmd.json`，插件轮询。零端口零鉴权 |
| 写防护 | **二次确认 + 审计**（时间/谁/对谁/做了什么，事后可查） |
| 注入默认 | **默认开**，但每实例可关；**建服与导入已有服务器时都要提示** |
| 用户删了 jar | **以开关为准**（开关是开就补回；想永久关去设置关） |
| 插件列表展示 | 标「面板自带」chip |
| 混合端 | **照注入**，但建服/导入时明确告知兼容性风险 |
| 物品展示 | **中文名 + 图标** |

### 二、⚠ 插件必须做成「纯旁观者」（我加的硬约束）
不注册**任何**事件监听（连 `PlayerJoinEvent` 都不注册），只用一个定时任务轮询
`Bukkit.getOnlinePlayers()` 再写 JSON。理由见下（混合端调研）。

### 三、OPanel 已评估并否决（别再查第二遍）
用户提议"不行就用 OPanel 调内部 API"，查下来**三处硬堵**：
1. **下不到**：不在 Modrinth（我们镜像搜 0 条），官方只放 GitHub Releases，而本机 GitHub 直连不通。
2. **要的数据不在公开 API 里**：官方文档只有 `/api/info`、`/api/players`（仅 kick/ban/op）、
   `/api/saves`、`/api/gamerules`、`/api/logs`。**没有坐标、没有背包** —— 背包编辑器和实时地图
   跑在 `/terminal` WebSocket 上，是**未公开的内部协议**。
3. **鉴权要逆**：三层加盐 MD5（access key → MD5(key+salt) → MD5(salt+hash)），还得先知道它的 access key。
4. **许可证 GPL-3.0**（README 与 LICENSE 一致；它游戏内 `/opanel about` 标的 MPL-2.0 是过时文案）。
   → 打进 exe 是合规负担；只能运行时下载，又回到第 1 条。
`/open-api/*` 虽是公开的，但只给 info/monitor/plugins/players，**恰好没有坐标和背包**。

### 四、关键发现：混合端让我们不必写 Fabric/Forge mod
混合端**对外暴露的都是 Bukkit API**，所以**一套 Bukkit 插件通吃「纯插件服 + 所有混合端」**：

| 核心 | 底层 | 版本 |
| --- | --- | --- |
| Arclight | Mixin 注入 Bukkit API 到 Forge/NeoForge/Fabric | 1.15.2–1.21.1（活跃，2000+ stars） |
| Mohist | Forge + Bukkit 层 | 1.7.10/1.12.2/1.16.5/1.18.2/1.20.x |
| CatServer | Forge + Bukkit | 1.12.2/1.16.5/1.18.2 |
| Cardboard | **Fabric mod** + Bukkit/Spigot/Paper 插件 | 1.16.5–1.21.x |
| Youer / Magma-Neo / Ketting | NeoForge/Forge + Paper/Bukkit | 现代版本 |

**但社区共识是混合端"兼容性尽力而为"**，大型模组服几乎跑不起来，且**大多数插件与 mod 开发者
明确拒绝在混合端上提供支持** → 一旦出事锅全是我们的。这就是"纯旁观者"约束的来源。

Tier 2（原生 Fabric/Forge mod）只剩"纯 mod 端不加混合层"这一小撮，押后。

### 五、为什么砍掉 Tier 0（读 .dat NBT）
用户直觉「Tier 0 太难受」，我复核后认同，把成本摊开：
1. NBT 要解析器（go-mc 依赖或自写 ~150 行）
2. **物品编码有两套**：1.20.5 前是 `tag:`（显示名还是 JSON 文本组件），1.20.5 起改成 `components:`，两种不兼容
3. 物品中文名我们没有（现有 `mcmod_zh.json` 只覆盖 mod）
4. 没材质图标
5. 落盘路径要拿真实存档验证
6. 陈旧度要 flush 兜

**更关键的是我自己吹错了它的最大卖点**：我说"离线玩家只有 Tier 0 能看到"—— 其实**插件也能**，
让插件按 UUID 缓存"最后一次快照"即可，玩家下线后快照还在。所以离线场景不需要 NBT。
剥掉这层后 Tier 0 独有价值只剩"原版服/纯 mod 服"，而国内是少数派 → 砍。

代价（已跟用户讲明）：**原版服与纯 mod 服点开玩家页会看到「本服类型不支持玩家数据（需插件体系）」**。

### 六、素材管线（已打真接口全部验证）
`中文名 + 图标` 这条路**实测可行且便宜**：

1. 版本清单：`https://piston-meta.mojang.com/mc/game/version_manifest_v2.json` → **HTTP 200**（最新 26.3）
2. 版本 JSON（清单里每个版本的 `url`，**别自己拿 jar 的 sha1 拼，会 404**）→ `assetIndex.url`
3. asset 索引 → `minecraft/lang/zh_cn.json` 的 hash →
   `https://resources.download.minecraft.net/{hash前2位}/{hash}` → **542 KB，8560 条**
4. 客户端 jar（版本 JSON 里 `downloads.client.url`，1.21.4 = 27 MB）

**实测体积**：item 贴图 644 张 **0.13 MB**；block 贴图 1039 张 0.29 MB；中文名表 0.55 MB。
→ **嵌进 exe 增量约 +1 MB**（11.4 → 12.4MB），完全可接受。
⚠ 客户端 jar 里**只有 `en_us.json`**，其他语言要单独从 `resources.download.minecraft.net` 下
（1.20+ 把语言包挪出 jar 了），别在 jar 里找 zh_cn。

已验证翻译键：`item.minecraft.diamond_sword` → 钻石剑；`block.minecraft.diamond_block` → 钻石块。

## 插件实时数据（第二阶段）：抽屉高度 bug + 审计日志闭环

### 一、抽屉被压成 214px —— 抓到真凶：入场动画留下的 identity transform
现象：`position:fixed; top:0; bottom:0` 的抽屉渲染成 `y=125, h=214`，与 CSS 字面矛盾。
**定性方法（值得复用）**：从出问题的元素往上逐层打印
`tag/class/pos/transform/backdropFilter/perspective/animation/fillMode/rect`，一眼看出
祖先链里有个 `div` 的 `transform` 是 `matrix(1, 0, 0, 1, 0, 0)`。

根因：`.stagger > *` 与 `.anim-in` / `.anim-in-x` 用的是
`animation: fadeUp ... both` + 关键帧 `to { transform: none }`。
**`fill-mode: both` 会把 100% 帧的 `transform: none` 永久钉在元素上，Chrome 归一化成 identity matrix**
—— 而「非 none 的 transform」就是一个 containing block。于是该元素内部所有 `fixed`
覆盖层都不再相对视口定位，而是撑满这个祖先（`.stagger` 的某个子元素只有 214px 高）。
同类坑还有 `filter` / `backdrop-filter` / `will-change` / `contain`。

两手一起修：
1. **覆盖层一律 `createPortal` 到 `document.body`**（`Dialog` 与 `Sheet`，`ConfirmDialog` 走 Dialog）。
   祖先只剩 body，以后谁再给页面加动画都踩不到。
2. `fill-mode: both → backwards`（这三处都没有 `animation-delay`，观感一模一样，
   但动画一结束动画属性就撤销，不再残留 transform）。

⚠ **这是全局存量 bug，不只在新面板**：`PlayersPanel` 原来的玩家抽屉（在 `.stagger` 里）
同样被压扁。`.stagger` 出现在 10+ 个面板里。

### 二、`go build ./cmd/server` 不会更新 `bin/serverbox.exe`
它把 `server.exe` 吐在**仓库根目录**。我用 schtasks 起的还是旧的 `bin/serverbox.exe`，
于是浏览器一直加载旧 assets（`index-D0zriyuJ.js`），而我改的 CSS 明明在磁盘上。
**判据：`curl 面板/assets/index-*.css | grep` 对比磁盘产物**，别信本地文件。
正确出包（同 build.sh）：`go build -trimpath -ldflags "-s -w -X main.version=dev" -o bin/serverbox.exe ./cmd/server`

### 三、`stale` 加 omitempty 会被吞（同类第三次）
`Stale=false` 是「我刚读过，是新的」，`undefined` 是「后端没提这回事」——两件不同的事。
已去掉 omitempty，并把断言加进 `TestCompanionZeroValuesSurviveJSON`。

### 四、`kill 面板` 会带走 MC 服务端
面板被 `taskkill /F` 时 stdin 管道关闭，Paper 读到 EOF 会自己退出（不是孤儿进程）。
所以「面板没托管但插件还在写数据」这个状态只在**手动开服**时出现，不是重启后的常态。

### 五、审计日志闭环
后端 `AuditLog` 原来没前端入口 —— 抽屉里写「每一步都会记进审计日志」却没地方看，
等于空头承诺。补了 `LivePanel` 的「操作日志」抽屉（区块头第三个按钮）：
列 时间/结果/做了什么/对谁/参数，失败的把原因挂下面；`op` 与 `gamemode` 参数都翻译成中文。
真点击闭环已验证：治疗 → 确认 → toast「已治疗 UIBot」→ audit 14 条 `heal ok:true`。

### 六、字号下限 11px
`.live-slot-name` 10.5px、`.live-count` 10px 都低于设计规范字阶下限，已提到 11px。

### 七、混合端导入挑错启动文件（真 bug，已修 + 回归测试）

Arclight 首次启动会**把 Forge 装进自己目录** → 根目录同时有 `arclight.jar` 和
`libraries/.../win_args.txt`。`DetectImport` 老逻辑「有 args.txt 就无条件优先」→
`JarPath` 变成 `win_args.txt`。而它**只有 JVM 参数、没有主类**
（主类在 jar 的 MANIFEST：`arclight.jar` → `io.izzel.arclight.server.Launcher`），
`buildArgs` 发 `@win_args.txt` → 起不来。

改法（`internal/daemon/import.go`）：新增 `isHybridLauncherName` / `hybridBaseType`，
**名单单一来源**（`classifyJar` 与 `DetectImport` 共用）；分支顺序改为
**混合端 jar > args.txt > 通用名 jar**；版本号从它刚装好的 Forge 目录名捡。

⚠ **普通 Forge 必须继续走 args.txt** —— 有反向护栏 `TestDetectImportPlainForgeStillUsesArgs`。
**已验证抓得住旧代码**：把条件改成「args 存在时混合端不优先」→ `TestDetectImportHybridBeatsForgeArgs`
如实变红并打印出 `win_args.txt`，还原后转绿。

### 十、面板启动方式（踩坑）

用 `.bat` 启动面板会**因为路径含中文而失败**：cmd 按 GBK 读 bat，`cd /d F:\项目\开服器\bin` 被读花 →

### 二十、bug1（严重）：代理端「不支持」的理由是错的，还印着空白

导入真 Velocity 后面板写的是：
`这个插件要求 Java 17 以上，而 ␣␣ 需要 Java 8。往 Java 8 的服务端里塞一个 Java 17 的 jar…`

### 四十、桌面端窗口（M6 起步）：先探构建链，再做壳

用户：「好了，做桌面端UI界面吧」。DESIGN.md 本来就规划了（Wails v2 + 托盘桌面端 + Web 同源），
按既定选型做，不另立方案。

**先验前提（本轮做对的第一件事）**：本机 `CGO_ENABLED=0` 且**没有 gcc**，
而 Wails 在 Windows 上要不要 CGO 决定这条路通不通 —— 所以先 `wails doctor` + 建最小工程 `wails build`：
**probe.exe 11.9MB、32 秒、无 gcc 也成功**。结论：v2.16 在 Windows 用纯 Go 的 WebView2Loader，**不需要 CGO**。

**关键取舍**：没做「内嵌前端 + 反代 /api」，而是让窗口首屏**整个 302 重定向**到守护进程地址。
理由：日志与实时数据都是 SSE，反代要求中间每层都不缓冲，而 AssetServer 那层不受我们控制 ——
一旦被缓冲，控制台就「卡住不动」，现场却像服务端不推数据。重定向之后 webview 的**源**就是守护进程本身，
Cookie / SSE / 相对路径全部天然成立。代价是 daemon 不在就没界面，所以补了自带等待页
（探活 → 健康就 302，否则自动拉起 + 每秒自刷新的「正在启动面板…」）——
**不能让用户看见浏览器的「无法访问此网站」**。

**两个真 bug（都是本轮现形的）**：
1. **拉起的守护进程监听到别的端口**：守护进程不带 `-addr` 就用自己保存的配置（本机是 `:23333`），
   而窗口在等 `:23456` → 两个进程都活着、窗口永远转圈，现场像「面板坏了」。
   护栏 `TestDaemonArgsAlwaysCarryAddr` 盯的是**参数本身**（这个 bug 的形态是「算对了但没传」）。
2. **关窗会把守护进程（及其管着的服）一起带走**：子进程默认沿用父进程控制台，
   **控制台一关 → CTRL_CLOSE_EVENT → 没装处理器就直接结束**。
   修法 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`（`cmd/desktop/proc_windows.go`）。

⚠⚠ **这条结论差点被我自己的测试夹具骗过去**：第一轮测「杀壳 → 守护进程也没了」，
看着像修复无效。真相是我从工具的控制台启动壳，壳与被它拉起的 daemon 共用那个控制台，
一杀整条一起走 —— **夹具干扰，不是产品行为**。反证：先独立启动 daemon（不由壳拉起），
再启动壳、只杀壳 → daemon 活着。最后用**计划任务**脱离我的控制台跑干净场景，确认修复有效。
→ **又一次印证：验证结论之前，先确认「我测的是产品，不是我搭的夹子」。**

**顺带记两条环境事实**：
- ⚠ `options.App` 上**没有 `OnSecondInstanceLaunch`**，它在 `SingleInstanceLock` **里面**；
  且 v2 **没有** `options.App.URL`（不能直接加载远程地址）→ 只能走 AssetServer 的 Handler。
- ⚠ 本会话 **PowerShell 工具再次返回空 stdout**，而且从 Bash 里调 powershell 会被安全策略拦。
  要用它做的事，改成「让它写文件、我从 Bash 侧读」（本轮截图脚本就是这么干的；
  但窗口截图仍拿不到 —— 工具所在会话读不到那个窗口句柄，如实说明，别假装截到了）。
- ⚠ `wails build` 的参数：**`-s`** 才是跳过前端构建（不是 `-skipfrontend`），另有 `-skipembedcreate`。

### 四十一、整合包（modpack）：竞品对比 + 实测判据 + 方案（用户要求「先对比，再讲怎么做」）

产出 `docs/MODPACK.md`。全部事实来自**实测**（打真接口 / 拆真文件 / 读真源码）：

**竞品对比（GitHub 全库 code search）**：MCSL2 里「整合包」只出现在报错文案与配置页；
MCSManager 里 `modpack` 只出现在一个 service 与 7 个语言文件 —— **两家都没有整合包导入**。
真正做这件事的全是专用 CLI（`nothub/mrpack-install`(Go)、`Patbox/mrpack4server`、`HarvelsX/Sugar`…），
**没有一个做成「面板里点一下」**。→ 这是差异点，而且我们的活是「把 CLI 流程搬进界面」，不是重写算法。

**实测判据（凭直觉一定会写错的两处）**：
1. Modrinth 搜索项自带 `server_side` / `client_side`。`Fabulously Optimized`（1799 万下载）
   就是 `server_side: unsupported` 的**纯客户端包** —— 市场上默认只列 `server_side != unsupported`
   就是「服务端整合包市场」，判据由接口给，不用猜。
2. `.mrpack` 里**没有模组本体**：只有 `modrinth.index.json` + `overrides/`；
   129 个模组全靠 `files[].downloads` 去 CDN 取 → **必须复用现有下载管理器**，别另写一条下载路。
   `dependencies` 直接给 `forge 47.4.10 / minecraft 1.20.1` → 建实例要的加载器与版本不用猜。
   判定：`env.server` = required(装) / optional(列出来让用户勾) / unsupported(不装)；
   覆盖文件只取 `overrides/` 与 `server-overrides/`。
   ⚠ **这一条被参考实现证实了**：`nothub/mrpack-install` 的 `overrides.go` 与 `update/command.go`
   用的是同一套判据（`Env.Server` 三档 + 两个前缀）。
3. 安全项：解压 `overrides/` 要防 **zip-slip**（条目名可能是 `../../…`）—— 包是第三方下载来的，
   每个条目都要校验「解压后仍在实例目录内」，与配置编辑器那三层路径防护同一条规矩。

**明确不做客户端整合包**，理由是定位：客户端整合包主体是光影/优化/按键配置，装服务端要么白占要么崩；
我们是开服器不是启动器，客户端那条线是 PCL2 的地盘（项目从第一天就定了不碰）。

分期：P0 本地 `.mrpack` 导入（含判定与拒绝文案）→ P1 市场（Modrinth，只列服务端可行的）
→ P2 CurseForge（要 key，且服务端包是单独发的）→ P3 整合包升级。
**P0 的解析器就是 P1 要用的那个**，先做这两步不返工。

### 四十二、整合包升级：计划文档 + 核心实现（U1–U3，用户指定先做这块）

用户确认对比对象就是 **MCSL2 / MCSManager**（已写进 `docs/MODPACK.md` 第六节），
并要求「写计划文档然后开工做整合包升级」。

**先说清一个硬依赖（写进文档了）**：升级没有地基就无处下手 —— 得先知道「这个实例来自哪个包、哪一版」，
而这只能靠**导入时写下的 packstate**。对着一个跑着的服务器目录靠比对文件反推包身份**不可靠**。
→ 所以实现顺序是 `packstate + 解析器` → `比对与文件操作` → 接界面。**导入不是升级的前置「功能」，
是前置「数据」。**

产出的三个纯逻辑模块（`internal/modpack/`，全部 LF、gofmt 干净）：
- `mrpack.go`：`modrinth.index.json` 解析 + 服务端/客户端分档 + **zip-slip 路径校验**；
  `dependencies` 直接给加载器与版本；`env.server` 三档（required 装 / optional 让用户勾 / unsupported 不装）。
  ⚠ **认不出的档位必须当 required** —— 当 unsupported 会把该装的模组悄悄漏掉，界面上完全看不出来。
- `packstate.go`：身份与「我们装进去的文件清单」，存 **`<实例目录>/.serverbox/packstate.json`**
  （跟实例走，不跟面板 data 目录走 —— 实例被搬走/还原后身份必须还在）。原子写（temp+rename）。
- `diff.go`：`BuildPlan(旧状态, 新包, 磁盘现状回调)` 纯函数 → 新增/变更/删除/保留/跳过 + 版本跳跃警告。

**三条安全底线（这功能最容易写坏的地方，逐条有测试）**：
1. **删除的判据是「它在旧 packstate 里」，不是「它不在新包里」** —— 用户自己丢进 mods/ 的一个都不能碰。
2. **磁盘那份与 packstate 记的对不上（用户改过）→ 不覆盖、不删除，列进「跳过」并说明**。
   默认覆盖等于悄悄吃掉用户的改动。
3. **游戏版本/加载器变了 → 标成「版本跳跃」并提示先备份** —— 那不是「更新一下」，是换了一台服。
   另外：目标版本若不再是服务端包（`ServerVerdict` 不 OK）→ **直接拒绝升级**，否则会把服务端清成
   一堆客户端模组。

**16 条测试，并按规矩验过它们抓得住写坏的实现**：临时拆掉底线②（改成「包里说了算」）→
`TestBuildPlanSkipsUserModifiedFiles` 与 `TestBuildPlanSkipsPathsUserAlreadyOccupies` 立刻变红并报
「覆盖了用户改过的文件」，还原后全绿。**这条不做，测试就只是装饰。**

⚠ 另记一条判据写法：`TestStateRoundTripAndNoNullLists` 的判据**必须放在序列化之后** ——
Go 里 nil slice 与空 slice 用 `==`/遍历都分不出，过一遍 JSON 才看得出是 `[]` 还是 `null`
（这是本项目重复踩过的坑，packstate 也是发给前端的集合字段）。

下一步是 U4（真升级：下载 + 落盘 + 删旧 + 写回 packstate）与接界面，以及 P0 的导入界面。

### 真机验收抓到的真 bug（车道测试为什么漏）
**上一版就有的覆盖文件全被误判「用户改过」跳过**（升级该覆盖的覆盖不了，界面看起来还很「安全」）。
根因：执行器给覆盖记账用落盘自算的 **sha1**（包里对覆盖不给哈希），而 api 层 `diskProbe` 收集
「按哪种哈希问磁盘」只看了 `old.Files`/`next.Files`，没看 `old.Overrides` → 覆盖路径回落默认 sha512，
与 sha1 记录永远对不上。修法：diskProbe 增加 `nextOv` 参数、收集两代覆盖的种类（键用
`modpack.DiskRelOfOverride`——顺手把私有 overrideDiskRel 导出成唯一换算）。
**车道测试漏掉它的原因：假环境 packstate 的 `Overrides` 灌的是空数组、主场景的覆盖是「新增」——
从没测过「上一版就有的覆盖」。测试数据的形态不真实＝那一路白测**（与「给代理端填 MCVersion」同款）。
回归 `TestUpgradeDoesNotSkipPristineOverrides` 先红后绿（红时 skip=2/replace=0，与真机一字不差）。
⚠ 修测试时自己先踩了夹具坑：v1/v2 的模组文件在假 CDN 没登记 → 404 → 装完 packstate.files 空，场景退化。

## 四十七、P1 收尾：三个只有「真跑一遍」才会发现的问题

P1 功能写完、28 个用例全绿之后，又在无头浏览器里真跑了一遍交互，抓到三件事。共同点：
**三个都逃过了全部断言。**

**① 点包之后版本区滚不到位（产品 bug，两层原因叠在一起）**

现象是「点了某一行，眼前几乎没变化」。第一反应是没滚，加上 `scrollIntoView` 后仍不对。

用探针把数字读出来才看清：
- 早滚（`picked` 一变就滚）：`scrollTop=979`，版本区顶距视口 **664px**；
- 手动再调一次 `scrollIntoView`：`scrollTop=1381`（已是上限），顶距 **262px**；
- 直接 `scrollTop=1643`：被夹到 1381。

两个独立的坑：
1. **`scrollIntoView` 会被「当时的可滚动高度」夹住。** 版本行还在异步拉取时页面只有骨架屏那么矮，
   此时滚只能滚到矮页面的底（979）。等十几行版本撑高页面，**滚动位置不会自己补上**。
   → 修：等 `vLoading` 落回 false 再滚（effect 依赖 `[picked, vLoading, versions.length]`），
   并用 `scrolledFor` 记「这个包的这一轮已经滚过了」，避免用户翻上去又点回来时反复弹。
2. **版本区是这一屏的最后一屏内容，它下面没有东西了。** 换到版本少的包（Better MC，8 行）时，
   页面总高不够，滚动上限天生放不下它 —— 实测停在 `top=427`，看着还是「没滚上来」。
   → 修：容器 `min-h-[70vh]`，给滚动留出余量。版本多的包本来就超这个高度，加了无副作用。
   修完两个包都稳在 `top=247`、可见 `true`。

用瞬间跳转不用 `behavior:'smooth'`：跨十几行的动画要一秒多，期间用户看到的还是那份列表，反而更像没反应。

**② 验证脚本自己制造的「假故障」（差点去改产品代码）**

同一个断言在第二次跑时变成 `位置: undefined`。原因不在产品：脚本点完包只等**区块标题**，
而标题在 `picked` 一变（React 同步提交）就有了，那时 `.mp-ver` 还是 `null`，
`getBoundingClientRect()` 抛异常被 `Runtime.evaluate` 吞掉 → 读回 `undefined`。
**看着像功能坏了，其实是探针跑早了。** → 等条件里必须写进「本次新增的那批元素」。
已补进 skill `headless-ui-verify` §12.9.1。

**③ 源站描述里的 Markdown 印到了屏幕上**

原则⑦⑧早就写着「给界面的字符串是纯文本」，但没人验证过源站到底给不给 Markdown。
这次直接打源站取样：热门整合包 **100 条里有 1 条**中招 —— `BattleArmory TACZ` 的描述在句尾插了
一对**不成对**的 `**`，原样印出来就是列表里挂着两个星号。不常见，但撞上了用户只会觉得
「这软件做的什么玩意」。→ `fetch.plainText()` 洗 `**`/`__`/`` ` ``/`[文字](链接)`/行首 `#`。

⚠ 关键取舍：**只洗成对的双字符标记，单个 `*` 和 `_` 一律不动**。模组 id 全是单下划线
（`mezz_config`/`fabric_api`），当斜体吃掉会**改坏名字**，而「改坏」不报错，只表现为用户搜不到东西 ——
这比留两个星号严重得多。护栏 `TestMarketDescriptionIsPlainText` 里专门留了这两条反例。
接口级也验了：`q=BattleArmory` 返回的描述里 `**` 已消失。

**验收**：`go test -short ./...` 6 包全 ok；`go vet` 无输出；tsc 0 error；
无头 CDP 四步（默认列表 / 点包滚动 / 换包再滚 / 移动 520 无溢出 `SW==CW`）全过；
接口实测描述无标记。

**⚠ 这轮没能用截图核对视觉**：本会话的图片通道被过滤，Read 读 PNG 返回的是「不支持图片」，
所以上面所有结论都来自 DOM 读数与接口报文，**没有一条是"看图看出来的"**。
真机视觉仍需人眼过一遍（市场页/版本层/移动端）。

## 四十八、市场筛选四件套：后端有接口、界面没入口（用户一眼看出来的）

收尾那轮我在市场上过了一遍，用户回一句「**没分类吗？**」。一查是真问题：

这就是原则⑦「有接口没入口＝空头承诺」。用户一句话抓到了我跑遍断言都没抓到的东西。

补的四组下拉（加载器 / 游戏版本 / 排序 / 数据源），**一改就重查**，不攒到按「搜索」——

  界面写着没筛、实际筛了，最容易被当成「搜索结果不对」。
- 空态三分支：筛窄了 / 被服务端滤掉了 / 真没有 —— 下一步完全不同。

**验证方式的两次自我修正（都值得记住）**：
1. **深链验不了这次改的东西**。深链只证明「读参数 + 首查」通；
   「点一下下拉列表当场就换」必须走真交互（原型 value setter + 冒泡 change，

2. **只看「已筛：加载器 Forge」那行等于没验** —— 界面自己写死两个字也能显示出来。

   （第一版脚本只比「首条有没有变」，而 forge 与未筛的首条**本来就是同一个包**，白判了。）

**⚠ 原生 `<select>` 的截断查不到**：`clientWidth` / `scrollWidth` 都不变，看几何永远看不出来。
只能自己用 `canvas.measureText` 配同一套字体量最长选项，再和「可用宽度 = 控件宽 − 内边距 − 箭头(22px)」比。

教训：**遇到「图在深色底上看不见」，第一件事是采这张图的像素，别猜作者是照什么底色画的。**
